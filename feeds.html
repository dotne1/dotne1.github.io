CVE-2026-65622

Published: 2026-11-24 09:17:39 CDT

Severity: N/A

CVSS Score: N/A

Improper Encoding or Escaping of Output vulnerability in ex-aws ex_aws_ses (ExAws.SES module) allows path injection into Amazon SES V2 request URLs. This vulnerability is associated with program file lib/ex_aws/ses.ex and program routines ExAws.SES.delete_contact_list/1, ExAws.SES.get_contact_list/1, ExAws.SES.update_contact_list/2, ExAws.SES.create_contact/3, ExAws.SES.get_contact/2, ExAws.SES.update_contact/3, ExAws.SES.delete_contact/2 and ExAws.SES.list_contacts/1. The V2 contact-list and contact functions interpolate the caller-supplied list_name into the request path without URI-encoding it, unlike the email address in the same functions which is passed through ExAws.Request.Url.uri_encode/1. An application that forwards untrusted input as a contact-list name lets an attacker embed /, .. or ? to escape the intended contact-lists/ path segment. A value such as x/../suppression/addresses/victim%40example.com makes a delete_contact_list/1 call arrive at the account-wide suppression list. The request is still signed with the application's own AWS credentials and sent to the configured SES host, so the impact is cross-resource request forgery inside the caller's own AWS account, not arbitrary SSRF. Applications that only use hardcoded or strictly validated list names are not affected. This issue affects ex_aws_ses: from 2.3.0 before 2.5.0.

CVE-2026-65621

Published: 2026-11-24 09:17:39 CDT

Severity: N/A

CVSS Score: N/A

ex_aws_s3 builds x-amz-meta-* request headers by interpolating user-supplied object metadata directly into header names and values without any validation. In ExAws.S3.Utils.build_meta_headers/1 (lib/ex_aws/s3/utils.ex), each :meta entry is turned into a header as {"x-amz-meta-#{k}", v} with no check for carriage return (CR), line feed (LF), or other illegal header bytes. Object metadata is routinely derived from end-user input (for example an upload service that lets users attach a comment or label to an object). When such input reaches ExAws.S3.put_object/4 or any other operation accepting the :meta option, a value containing CR/LF is carried unchanged into the outbound header list. If the configured HTTP adapter does not neutralize header values before writing them to the socket, the embedded CRLF starts a new header line, allowing an attacker to inject arbitrary headers into (or split) the HTTP request the library sends to the S3 endpoint. This is an HTTP header (CRLF) injection leading to HTTP request splitting. The practical impact depends on the HTTP adapter, and no authentication is required beyond the ability to influence object metadata. This issue affects ex_aws_s3: from 2.0.0 before 2.6.0.

CVE-2026-63585

Published: 2026-11-24 09:17:38 CDT

Severity: N/A

CVSS Score: N/A

ExAws.S3 constructs S3 ACL grant headers (such as x-amz-grant-read and x-amz-grant-full-control) in format_grant_header/1 by interpolating grantee identifiers into a quoted, comma-separated list without escaping. Grantee email and id values are wrapped in double quotes and joined with a comma, but double-quote, comma, and CR/LF characters in the value are not neutralized. An application that passes an attacker-influenced grantee value (for example an email address taken from a "share this object" feature) into an ACL grant option (grant_read, grant_write, grant_read_acp, grant_write_acp, or grant_full_control) lets the attacker close the quoted token and inject an additional grantee, such as the attacker's own canonical id or the predefined AllUsers group URI, into the header. S3 then applies the injected grantee, granting an arbitrary principal the same permission (up to full control or public access) in an unintended ACL grantee-injection and privilege-escalation issue. This issue affects ex_aws_s3: from 2.0.0 before 2.6.0.

CVE-2026-63584

Published: 2026-11-24 09:17:38 CDT

Severity: N/A

CVSS Score: N/A

Improper Neutralization of CRLF Sequences ('CRLF Injection') vulnerability in ex-aws ex_aws_s3 allows HTTP header injection via an attacker-controlled copy-source key. ExAws.S3.upload_part_copy/8 in lib/ex_aws/s3.ex builds the x-amz-copy-source request header by interpolating the source bucket and object key directly into "/#{src_bucket}/#{src_object}" with no percent-encoding. The sibling function put_object_copy percent-encodes the bucket and each path segment before assembling the same header, but upload_part_copy skips encoding entirely. When the source key is derived from untrusted input, reserved characters (spaces, ?, &, =) pass through verbatim and corrupt the copy-source reference, so the copy targets the wrong object or fails. A key containing \r or \n can split or inject additional headers into the outgoing HTTP request, depending on how the configured HTTP backend serializes headers. Applications that pass a source bucket or object key derived from untrusted input to ExAws.S3.upload_part_copy/8 are affected. Applications that only ever pass trusted, well-formed keys are not affected. This issue affects ex_aws_s3: from 2.0.0 before 2.6.0.

Externally Controlled Reference to a Resource in Another Sphere vulnerability in ex-aws ex_aws_s3 allows an attacker who controls an S3 bucket name to make presigned URLs and presigned POST forms point at a host of their choice. With virtual_host: true, s3_accelerate: true or bucket_as_host: true, ExAws.S3.presigned_url/5 and ExAws.S3.presigned_post/4 build the URL from the bucket name without checking it. CVE-2026-63581

Published: 2026-11-24 09:17:37 CDT

Severity: N/A

CVSS Score: N/A

XML Injection vulnerability in ex-aws ex_aws_s3 (ExAws.S3 module) allows an attacker to inject arbitrary XML configuration elements into S3 bucket-configuration request bodies via unescaped, caller-supplied values. This vulnerability is associated with program files lib/ex_aws/s3.ex and program routines ExAws.S3.put_bucket_logging/2, ExAws.S3.put_bucket_notification/2, ExAws.S3.put_bucket_replication/2, ExAws.S3.put_bucket_website/2. The bucket-configuration body builders construct their XML by interpolating caller-supplied values directly into the request body without escaping, and never route them through the module's own escape_xml_string/1 helper. A value containing XML metacharacters (<, >, &, quotes) can close the intended element early and open attacker-chosen elements, which the builder's trailing closing tag then closes, keeping the document single-rooted and well-formed. In a multi-tenant application where tenants configure their own bucket settings, an attacker who can influence one of the interpolated field values (for example the logging target, a notification ARN, a replication destination or Account, or a website redirect HostName) can inject arbitrary configuration nodes into a request the application signs and sends to AWS. The affected builders are reached through the public functions put_bucket_logging/2, put_bucket_notification/2, put_bucket_replication/2, and put_bucket_website/2. This issue affects ex_aws_s3: from 2.5.9 before 2.6.0.

XML Injection vulnerability in ex-aws ex_aws_s3 allows an attacker who controls tag keys or values to inject forged tag entries into S3 object and bucket tagging requests. ExAws.S3.put_object_tagging/4 and ExAws.S3.put_bucket_tagging/2 in lib/ex_aws/s3.ex build the request body by interpolating tag keys and values directly into and elements via to_string/1, without applying the module's existing escape_xml_string/1 helper (which delete_multiple_objects already uses for object keys).
