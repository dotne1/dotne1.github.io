CVE-2026-136641

Published: 2026-11-25 04:17:14 CDT

Severity: MEDIUM

CVSS Score: 6.8

Pydantic AI Harness's PlaywrightBrowser enforces its egress policy on HTTP requests and page WebSockets, but not on WebRTC or WebTransport connections, WebSockets opened with WebSocketStream, or the requests the browser itself sends for FedCM. A page the agent opens can make the browser send WebRTC (STUN and TURN), WebTransport and WebSocketStream traffic, and FedCM requests, to hosts and ports that the policy refuses, including under a policy that limits every request kind to an allowlist. This affects applications that use PlaywrightBrowser to open pages an attacker can influence. The traffic is each protocol's connection setup, sent to a destination the page chooses. A page can learn whether a target answers a STUN request. No response body from an ordinary internal service was readable through WebRTC, WebTransport or FedCM. A WebSocketStream is an ordinary WebSocket that the WebSocket guard does not see, opened from a page, a frame or a worker, and the page reads what the server sends, including from a private address. Chromium's Local Network Access blocks WebTransport from public pages to private addresses, but does not block WebRTC. A FedCM call (navigator.credentials.get with an identity provider) makes the browser fetch the provider's /.well-known/web-identity, config, accounts and client metadata URLs. The page chooses the config URL's path and the client ID, so it can send data to a host outside allowed_domains or listed in blocked_domains. The accounts request carries the provider's cookies from the browser profile. FedCM requires a provider origin that is HTTPS or loopback. The assumed attacker is a third party with no access to the application who controls script on a page the agent opens. Under an enforced egress policy, which is the default, pydantic-ai-harness 0.74.0 removes RTCPeerConnection, webkitRTCPeerConnection, WebTransport, WebSocketStream, IdentityCredential and IdentityProvider from every page and frame, refuses FedCM calls to navigator.credentials.get, and launches Chromium with FedCM and WebSocketStream turned off. These paths stay outside the policy: WebTransport from workers; WebSocketStream from workers in a browser reached over cdp_url; WebTransport in sandboxed iframes that Chromium runs in their own process (headless=False and cdp_url); and documents loaded before attachment under cdp_context='default'. Upgrade pydantic-ai-harness to 0.74.0 or later. For the paths the upgrade leaves open, and until you upgrade, run the browser behind a network egress filter that also covers UDP, or do not open untrusted URLs with PlaywrightBrowser.

CVE-2026-134792

Published: 2026-11-25 04:17:14 CDT

Severity: N/A

CVSS Score: N/A

When the proxy option isn't set, HttpClient takes the proxy from environment variables like http_proxy or HTTP_PROXY. On web servers, it ignores HTTP_PROXY, because PHP puts the Proxy request header there (the httpoxy issue). On the CLI SAPI, it read HTTP_PROXY from $_SERVER, where PHP also puts the environment. HTTP workers that run under the CLI SAPI put the headers of each request in $_SERVER too. This is the case of spiral/roadrunner-http, which the RoadRunner runner of php-runtime uses, and of baldinof/roadrunner-bundle and php-pm. A client could then send a Proxy header to choose the proxy of the requests that the application sent while handling its request. That proxy received the full requests to http:// URLs, with their credentials, and could forge the responses. For https:// URLs, it learned the host and port through CONNECT. NativeHttpClient is affected since Symfony 4.3.0, AmpHttpClient since 5.1.0, and CurlHttpClient since 4.4.40, 5.4.7 and 6.0.7. On the CLI SAPI, HTTP_PROXY is now read from the environment with $_ENV and getenv(), never from $_SERVER. Other SAPIs still ignore it.

CVE-2026-134791

Published: 2026-11-25 04:17:14 CDT

Severity: N/A

CVSS Score: N/A

Since Symfony 7.2, expressions can contain comments. The lexer used a regular expression to find the end of a comment. When a /* was never closed, this regular expression scanned the rest of the expression, and the lexer then went on with the next character. So each /* scanned the rest of the expression again. Linting 192 KB of /* took 9 to 11 seconds, and 96 KB took 34 seconds without PCRE JIT. The lexer runs before the parser and its nesting limit. Any code that lints or parses untrusted expressions is affected, including the ExpressionSyntax validation constraint. A Length constraint on the same value doesn't help, since the validator runs both constraints. The lexer now uses strpos() to find the end of a comment, and a comment that is never closed throws a SyntaxError. Such expressions were already invalid. Lexing takes linear time again.

CVE-2026-134790

Published: 2026-11-25 04:17:14 CDT

Severity: N/A

CVSS Score: N/A

The fix for CVE-2017-16652 restricts the redirects of HttpUtils::createRedirectResponse() to the host of the request. When framework.session.cookie_domain is set, it also allows the subdomains of that domain. To check a target, it read the host of the URL up to the first "/". But browsers also end the host at "\", "?" and "#". So with the cookie domain .example.com, a target like https://evil.test?.example.com passed the check, and the browser went to evil.test. Applications are exposed when framework.session.cookie_domain is set. The default success and failure handlers of form_login redirect to the _target_path or _failure_path of the request. A login link can then send the user to another site right after a successful login, for example to ask for the password again. HttpUtils now ends the host of a target where browsers do, before checking it against the allowed domains.

CVE-2026-133762

Published: 2026-11-25 04:17:14 CDT

Severity: N/A

CVSS Score: N/A

Since Symfony 7.4.0, FrameworkBundle chooses the error renderer from the runtime mode of the application, which comes from the APP_RUNTIME_MODE env var. When this variable isn't set, the cli, phpdbg and embed SAPIs default to the CLI mode, and errors are rendered with CliErrorRenderer. This renderer dumps the whole exception, and it did so even when debug was off. HTTP workers that run under the CLI SAPI and don't set APP_RUNTIME_MODE then sent these dumps as error responses in production. They contain the messages, file paths and traces of the exceptions. Some exceptions reference the request, like the access denied errors of access_control rules. Their dump then contains the server parameters, with all the environment variables of the application. This affects, for example, the RoadRunner, Swoole and ReactPHP runners of php-runtime, and baldinof/roadrunner-bundle before 3.2.4. The worker mode of FrankenPHP sets the variable and isn't affected. The CLI renderer is now used only in debug mode.

CVE-2026-133761

Published: 2026-11-25 04:17:14 CDT

Severity: N/A

CVSS Score: N/A

CsvEncoder::decode() splits each header cell on the key separator, . by default, and nests the decoded rows one level per separator, with no limit. PHP frees nested arrays recursively, so freeing data that is nested deeply enough overflows the C stack and crashes the process. With a stack of 8 MB, a CSV body of 448 KB is enough. Each row also builds all the levels of its headers again. With a deep header, a CSV body of 2 KB made of short rows allocates more than 128 MB. A body of 1 MB keeps the CPU busy for 10 seconds or more. Any code that decodes untrusted CSV with the Serializer is affected. From Symfony 7.4.0, this included every #[MapRequestPayload] argument that doesn't restrict acceptFormat, until 7.4.23 and 8.1.11 stopped decoding CSV payloads by default. CSV headers can now be nested up to 512 levels, the default depth of json_decode(). Decoding also stops when the rows go through more than 16 header levels, or create more than 4 arrays, per byte of data. A header row of up to 5 levels always fits, whatever the rows contain. Beyond these limits, decode() throws a NotEncodableValueException, which #[MapRequestPayload] turns into a 400 response.

CVE-2026-133760

Published: 2026-11-25 04:17:13 CDT

Severity: N/A

CVSS Score: N/A

The fix for CVE-2026-109449 made the expression parser check the nesting level of long expressions. This check exists since Symfony 5.4.54, 6.4.48, 7.4.21 and 8.1.9. The parser builds a ?: b with the node of a used twice, and the check walked every path to every node. With nested short ternaries, the number of paths doubles at each level, so an expression of 256 bytes never finished parsing. The expression needs no variable and no function. Any code that parses or lints untrusted expressions is affected, including the ExpressionSyntax validation constraint. evaluate() and compile() parse the expression first, so they hang too. The nesting check now skips the nodes it already checked, so it takes linear time again. evaluate(), compile() and the messages of runtime errors now use the node of a once, so a is evaluated once, as in PHP.
