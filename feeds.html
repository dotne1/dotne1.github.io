CVE-2026-16670

Published: 2026-11-24 18:17:12 CDT

Severity: MEDIUM

CVSS Score: 4.0

MCUboot's PSA-crypto ECDSA adapter parses the RFC 5480 DER signature with parse_signature_from_rfc5480_encoding() in boot/bootutil/include/bootutil/crypto/ecdsa.h, which takes no length argument. bootutil_ecdsa_verify() explicitly discards the signature length ((void)slen;) and the parser walks the encoding using length bytes read from the buffer itself (r_len = sig[3], then a derived s_len), with no check that those offsets stay within the supplied signature. Because this parsing runs before psa_verify_hash(), a malformed signature triggers the read whether or not the signature is valid. In bootutil_img_validate() (boot/bootutil/src/image_validate.c:404) the ECDSA signature TLV is gated only by len > sizeof(buf), since EXPECTED_SIG_LEN() is the constant 1 for ECDSA; len is attacker-controlled in the range 0..128 and is copied into the 128-byte stack buffer buf. With a crafted r_len (e.g. sig[3] = 255) the parser's memcpy reads roughly 130+ bytes past the end of buf, an out-of-bounds read of adjacent stack memory. Reaching the signature case only requires a key TLV that matches a trusted public key (public material), so the path is effectively pre-authentication. The defect is gated to the PSA crypto backend (MCUBOOT_USE_PSA_CRYPTO) with MCUBOOT_SIGN_EC256/MCUBOOT_SIGN_EC384 (and MCUBOOT_SIGN_EC384 always builds with PSA); the in-tree CC310, TinyCrypt, and mbedTLS adapters use different decoders and are not affected. This is not a signature bypass: the over-read bytes feed a verification that fails closed and are never returned to the attacker, so there is no information leak. The impact is bounded to a possible fault/denial-of-service on memory layouts where the read crosses an unmapped region; on typical flat-memory MCUs it reads adjacent RAM without faulting. This vulnerability was reported independently twice: by NVIDIA Project Vanessa on 2026-06-22, and by Kai Phan (@kaimandalic) on 2026-07-19 as GHSA-r44p-8v6p-hqv4, which is closed as a duplicate of this advisory. Both original reports are reproduced in full below. The second report additionally observes that bootutil_ecdsa_parse_public_key() discards its end pointer ((void)end;, ecdsa.h:446). That observation is correct, but it is not part of this vulnerability and is not counted in the severity: the buffer it parses is bootutil_keys[key_id].key, the compiled-in trusted key store (image_ecdsa.c:54-55), so no attacker-controlled data reaches that parse. It is a robustness gap on the same code path and should be closed alongside the signature-parser fix. Note also that the second report's proof-of-concept models the signature buffer as an 8-byte heap allocation and therefore reports a heap overflow; in MCUboot the buffer is the 128-byte stack array buf, gated by len > sizeof(buf), so the real over-read is of adjacent stack memory.

CVE-2026-16669

Published: 2026-11-24 18:17:11 CDT

Severity: LOW

CVSS Score: 2.0

MCUboot's Espressif port omits zeroization of two sensitive stack buffers in boot/espressif/hal/src/flash_encrypt.c. In check_and_generate_encryption_keys(), the freshly generated XTS-AES flash-encryption key is held in the stack array keys[BLOCKS_NEEDED][32] (flash_encrypt.c:216), written to eFuse via esp_efuse_write_keys(), and the function returns (flash_encrypt.c:243) without scrubbing it. In esp_flash_encrypt_region(), the plaintext flash sector buffer buf (flash_encrypt.c:454) retains the last sector's cleartext at both the success and flash_failed returns. Neither path performs a memset/bzero/mbedtls_platform_zeroize, even though the same port already does bzero for key digests in boot/espressif/hal/src/secure_boot.c. The affected code runs only on the Espressif port with CONFIG_SECURE_FLASH_ENC_ENABLED, and only during the one-time first-boot provisioning pass when flash encryption is not yet enabled (boot/espressif/main.c); on subsequent boots the buffers are never created. Recovering the residue requires an out-of-band stack/RAM-disclosure primitive — JTAG/debug halt, UART ROM download, a core/crash dump, or a warm-boot RAM scrape — captured during that single provisioning boot. Under the recommended CONFIG_SECURE_FLASH_ENCRYPTION_MODE_RELEASE plus secure boot, those channels are fused off and no exposure exists. The practical impact is a low-severity, defense-in-depth hardening gap: a flash-encryption key (and last plaintext sector) may linger in bootloader stack memory. Because the eFuse key block is burned read+write-protected, the transient stack copy is the only readable copy, and only during one boot; in a development build where a disclosure channel is open, an attacker with that capability can usually already read the still-plaintext flash directly, so the marginal confidentiality gain is small. Confirming real-world recovery depends on a specific SoC/debug configuration not exercisable from source alone.

CVSS Score: 6.2

The Cypress/PSoC6 flash-map backend in boot/cypress/cy_flash_pal/cy_flash_map.c guards every flash access with assert() against the wrong struct field. flash_area_read(), flash_area_write(), and flash_area_erase() check assert(off < fa->fa_off) and assert(off + len < fa->fa_off), comparing the area-relative off against the partition's absolute base address fa->fa_off instead of its length fa->fa_size. Because fa_off is a large absolute address, realistic out-of-partition offsets pass the check even in a debug build, and under NDEBUG the asserts are removed entirely. The access then proceeds as memcpy() (or a flash row op) at fa->fa_off + off with no enforcement. The MCUboot core does not bound image-region offsets itself; it relies on flash_area_read() returning an error. During pre-authentication image validation, bootutil_img_hash() in boot/bootutil/src/bootutil_img_hash.c loops over ih_hdr_size + ih_img_size + ih_protect_tlv_size — all attacker-controlled header fields of the still-unverified update image — calling flash_area_read(), and the TLV iterator in boot/bootutil/src/tlv.c reads attacker-derived offsets the same way. An attacker who can stage a crafted image in the secondary/update slot (via OTA, DFU, or serial recovery, depending on the product) declares an oversized ih_img_size, causing reads far past the partition. A correct backend would reject these and fail validation cleanly; the Cypress backend does not. The out-of-bounds access is in the source address of the copy — the destination buffer is correctly sized — so there is no memory corruption, no information disclosure to the attacker (the data is only folded into a hash that still fails the signature check), and no authentication bypass. The realistic impact is a bus fault or hang when the computed absolute address lands on an unmapped or peripheral region of the PSoC6 address map: the bootloader crashes instead of rejecting the bad image, an availability (denial-of-service) impact. The defect is specific to the Cypress/PSoC6 port; mainline Zephyr/sim/mynewt backends are unaffected. The identical broken guard in the write/erase primitives is a latent out-of-bounds-write gap, but no attacker-controlled out-of-bounds offset was found to reach those (serial-recovery uploads are bounded by the core), so the reachable memory-safety bug is the out-of-bounds read.

CVE-2026-16666

Published: 2026-11-24 18:17:11 CDT

Severity: MEDIUM

CVSS Score: 5.7

When MCUboot resumes an interrupted image swap it takes the number of bytes to move straight from the flash-resident status trailer. In boot_swap_image() (boot/bootutil/src/loader.c) the fresh-swap branch recomputes copy_size from the image headers and is bounded — swap_run() in boot/bootutil/src/swap_move.c carries an explicit "not enough free space" check (last_idx >= first_trailer_idx) — but that check runs only inside if (boot_status_is_reset(bs)). On the resume branch the code instead does boot_read_swap_size(fap, &bs->swap_size); copy_size = bs->swap_size; and passes the value to swap_run() with no re-derivation and no bound. swap_run() turns that byte count into a sector index by summing sector sizes until it reaches the count, with no ceiling on the real sector count: find_last_idx() in swap_move.c and swap_offset.c, and find_last_sector_idx() in swap_scratch.c, are all while (1) loops. The resulting index is fed to boot_img_sector_off() / boot_img_sector_size() (boot/bootutil/src/bootutil_priv.h), which index the fixed BOOT_MAX_IMG_SECTORS sectors[] arrays with no bounds check. Past num_sectors the loop reads zero-initialised — and past BOOT_MAX_IMG_SECTORS, adjacent-struct — entries; a sector size of 0 makes the loop never terminate, and a bogus computed offset is handed to boot_erase_region() / boot_copy_region() as an out-of-bounds flash erase or copy. MCUboot itself only ever writes a validated, slot-bounded swap_size (swap_misc.c, fixup_revert()), so reaching the defect requires writing the trailer from outside. Serial recovery provides exactly that: an upload writes attacker bytes contiguously from offset 0 of the primary slot (boot/boot_serial/src/boot_serial.c, via flash_area_id_from_multi_image_slot()), bounded only by img_size <= area_size, so it controls the whole trailer — magic, swap_info, op/idx/state and swap_size. The resume gate boot_status_is_reset() keys solely on those op/idx/state fields, and boot_find_status() explicitly trusts valid magic as implying valid metadata. A forged in-progress status with an oversized swap_size therefore drives the unbounded walk during swap setup — before the primary image's signature is validated, and serial recovery is unauthenticated by design. The outcome is an out-of-bounds flash erase or copy, or a non-terminating loop, inside the bootloader: an unbootable or bricked device, with the possibility of bootloader memory corruption. That exceeds what serial recovery is designed to grant, which is only the ability to stage an image that must still pass signature verification. Exposure requires a swap-based update backend — MCUBOOT_SWAP_USING_MOVE (the default for swap builds), MCUBOOT_SWAP_USING_SCRATCH or MCUBOOT_SWAP_USING_OFFSET; overwrite-only, direct-XIP and RAM-load builds are unaffected — together with MCUBOOT_SERIAL_RECOVERY. Without serial recovery the path is only reachable by an attacker who can already write flash directly, which is outside the threat model. The fix is to treat the trailer's swap_size as untrusted: reject or clamp it in boot_swap_image() before it becomes copy_size, bounding it by the primary slot's usable image area (sector count x sector size, excluding the trailer) rather than the raw flash_area_get_size(), and aborting recovery with a non-zero error on overflow. The same guard should cover the independent boot_read_swap_size() reads in each backend's boot_read_image_header().

CVE-2026-16668

Published: 2026-11-24 17:17:32 CDT

Severity: LOW

CVSS Score: 2.4

The vendored zcbor decoder's zcbor_any_skip() in boot/zcbor/src/zcbor_decode.c descends one C-stack frame per level of CBOR nesting. On a list or map it copies the decoder state (memcpy(&state_copy, state, sizeof(zcbor_state_t))) and recurses once per member, with no depth cap: the skip path does not use zcbor's backup stack, and ZCBOR_MAX_ELEM_COUNT is SIZE_MAX, so nothing bounds how deep the recursion goes. That function is reached on attacker-controlled bytes before any authentication. MCUboot's serial-recovery command parser decodes SMP/CBOR requests with zcbor_map_decode_bulk() (boot/boot_serial/src/zcbor_bulk.c), which skips any map key it does not recognise by calling zcbor_any_skip() on the encoded value; the echo handler in boot/boot_serial/src/boot_serial.c calls it directly on the same footing. Both run during image upload, long before the uploaded image's signature is checked. The default receive buffer is MCUBOOT_SERIAL_MAX_RECEIVE_SIZE = 512 bytes and each nesting level costs a single byte to encode (0x81), so roughly 500 levels of nesting fit in one request — comfortably more than a bootloader's stack can absorb, since every frame carries a full zcbor_state_t copy plus locals. The impact is availability only: the bootloader's stack overflows and the device faults or hangs during recovery. There is no controlled out-of-bounds write that escapes the DFU buffer, no disclosure, and no authentication bypass — the recursion grows the stack with the decoder's own internal state. Whether a given board actually exhausts its stack depends on that board's bootloader stack size, which we did not measure; the fix is nevertheless unconditional, because an unauthenticated pre-authentication code path must not have its safety depend on a per-board stack margin. Exposure requires MCUBOOT_SERIAL (serial/SMP recovery), which is not enabled by default, and recovery entry is normally gated on a physical pin (CONFIG_BOOT_SERIAL_ENTRANCE_GPIO / PIN_RESET), with a no-valid-image fallback path. Products that expose serial recovery over an externally reachable transport, or that fall into recovery when no valid image is present, are the ones at risk. The fix is to bound the skip: thread a recursion-depth counter through zcbor_any_skip() (or have zcbor_map_decode_bulk() reject values nested beyond a small constant) and fail once the limit is exceeded — equivalently, take the bounded-skip implementation from upstream zcbor.
