CVE-2026-96354

Published: 2026-11-24 05:17:21 CDT

Severity: N/A

CVSS Score: N/A

Missing Authorization vulnerability in the public project REST API of Apache Texera (incubating). The public project API did not check that a project had been made public before granting the caller read access to it. Any authenticated user with an approved account (the REGULAR or ADMIN role; new accounts need administrator approval by default) could give themselves lasting read access to other users' private projects and to the private workflows in them, including their version and execution history. Only deployments in which users have created projects are affected; the project feature is hidden in the web UI by default. This issue affects Apache Texera: from 1.1.0-incubating before 1.3.0-incubating. Users are recommended to upgrade to version 1.3.0-incubating, which fixes the issue by removing the deprecated project feature and its data. If you cannot upgrade immediately, configure the reverse proxy in front of Texera to reject every request whose path starts with /api/project, /api/public/project or /api/access/project, and every request whose path contains ';', which the Texera server ignores when routing. Respond with 403 or 404, not 401: from 1.2.0-incubating the web UI treats a 401 as an expired session, and the workflow pages request the project list when they load. Unless an administrator has enabled the project feature, this does not affect other functionality; those project-list requests are simply rejected. Make sure the Texera server is reachable only through that proxy. Blocking and upgrading do not undo access obtained earlier. Before upgrading, review the project_user_access table, which remains empty unless someone has used the feature: treat any READ grant on a project that is not listed in public_project, and that the project's owner did not give, as suspect. The upgrade deletes this table. Removing a grant does not remove copies the user may already have made of the workflows.

CVE-2026-82446

Published: 2026-11-24 05:17:21 CDT

Severity: N/A

CVSS Score: N/A

Description When StormCrawler fetches a host's `/robots.txt` and receives a redirect, `HttpRobotRulesParser` resolves the `Location` header and re-fetches the target for up to five hops. The loop checks neither the scheme, the host nor the port of the resolved target, and it is not governed by `http.allow.redirects`, which only affects the page fetch. A crawled site can therefore point the robots.txt fetch at any address reachable from the fetcher worker, including loopback interfaces, private ranges and cloud metadata endpoints. Every crawled URL triggers a robots.txt fetch on a cache miss, so no unusual configuration is required to reach the loop. The fetched body is only parsed as robots rules and is not returned to the caller, so the read itself is blind. The more direct impact is on credentials: the okhttp protocol applies its configured request headers, including the `Authorization` header built from `http.basicauth.user` and `http.basicauth.password` and anything in `http.custom.headers`, to every request it makes. Because StormCrawler follows the redirect itself and issues a new request, okhttp's own removal of the `Authorization` header across a host change does not apply, and the operator's crawl credentials are delivered to the host the redirect names. The connection-time IP filter, `http.filter.ipaddress.include` and `http.filter.ipaddress.exclude`, is installed as an okhttp network interceptor on the same client and does apply to these hops when it is configured. It ships with no rules, which is why the path is reachable in a default configuration. URL filtering never applies, because the robots.txt fetch does not pass through the outlink filter chain. Mitigation Upgrade to 4.0.0, where a robots.txt redirect is followed only when the target uses http or https and shares scheme, host and port with the URL it was reached from. Deployments that legitimately serve robots.txt through a cross-host redirect can restore the previous behaviour with `http.robots.redirect.crosshost.allow`. Users who cannot upgrade immediately should set `http.filter.ipaddress.exclude` to cover loopback, private, link-local and CGNAT ranges, which is enforced after DNS resolution and therefore also on redirect hops. Operators who configure `http.basicauth.*` or `http.custom.headers` for a crawl should assume those credentials may have been sent to third-party hosts and rotate them, and should scope credentials by running a separate topology per origin. Credit Independently reported to the Apache StormCrawler PMC by n0mi1k, with a proof of concept. Also found by the ASF -- using Claude agents to study the security of open-source projects, validated and reported by Apache StormCrawler.

CVE-2026-82445

Published: 2026-11-24 05:17:21 CDT

Severity: N/A

CVSS Score: N/A

Description The SQL status backend serialises per-URL metadata into a single column by concatenating a tabulation, the key, an equals sign and the value, with no escaping. On read-back the string is split on the same two characters, so the round trip is not injective: a value that contains a tabulation returns as one or more additional keys that were never written. Values on that path are supplied by crawled servers. `FetcherBolt` records the raw `Location` header of a redirect as `_redirTo`, and `_redirTo` is part of the default `metadata.persist` set, so a redirect whose `Location` contains a tabulation followed by `key=value` pairs introduces those keys into the crawler's own control metadata on the next scheduling cycle. Several control keys are read without a prefix, so the injected keys are live: `http.proxy.host`, `http.proxy.port`, `http.proxy.user` and `http.proxy.pass` among them, as well as scheduling and request-shaping keys such as `depth`, `max.depth`, `crawl.delay`, `http.content.limit` and `isSitemap`. Where a proxy manager is configured, the consequence is not limited to corrupted scheduling data. `SingleProxyManager.getProxy(Metadata)` consults the per-URL metadata first and returns what it finds, so an injected proxy host and port take precedence over the operator's configured proxy and subsequent fetches, together with any configured `Authorization` header, are routed through a host the crawled content chose. A related defect in `AbstractStatusUpdaterBolt` compounds this: an injected `status.store.as.is.with.nextfetchdate` that is not a valid instant escapes the enclosing try/catch and stops the bolt, and because the stored row is replayed the failure repeats. Deployments using the OpenSearch or Solr status backends are unaffected, because those serialise metadata structurally. Mitigation Upgrade to 4.0.0, where the metadata column is written in an escaped form behind a format marker, rows written by earlier versions are still decoded unchanged, and the stored next-fetch-date is parsed defensively. The fix does not repair rows written before the upgrade. Operators using the SQL status backend should inspect the metadata column of an existing status table for tabulation characters and remove the affected rows, and should assume any proxy credentials configured for the crawl may have been exercised through an attacker-chosen proxy and rotate them. Users who cannot upgrade immediately can remove `_redirTo` from `metadata.persist` to close the demonstrated path, though other crawled values reaching persisted metadata remain. Also found by the ASF -- using Claude agents to study the security of open-source projects, validated and reported by Apache StormCrawler.

CVE-2026-82444

Published: 2026-11-24 05:17:21 CDT

Severity: N/A

CVSS Score: N/A

Description `CookieConverter.getCookies` decides which stored cookies to attach to an outbound request. The applicability check is nested inside a test for the presence of a `Domain` attribute, so a cookie without one, which is the ordinary form of a session cookie, skips scoping entirely and is returned for whatever target URL was passed. RFC 6265 requires the opposite: a cookie with no `Domain` attribute is host-only and belongs to the host that set it. Two further defects sit in the same method. The domain comparison has no notion of a registrable domain, so a `Domain` value of `com` matches every host under it, and the comparison returns true when it throws, so a failure to evaluate the check admits the cookie. Neither the converter nor `MetadataTransfer`, which carries the stored cookie to outlinks, ever considers the host that issued it. Cookie handling is opt-in: it requires `http.use.cookies` to be set to true, which is not the default, and the cookie key to be listed in `metadata.transfer`. The documented recipe does not work as written, because the `metadata.transfer` example in the internals documentation names `set-cookie` while the key present in metadata is `protocol.set-cookie` and the transfer matches key names exactly. Deployments affected are therefore those where an operator determined the correct key, enabled cookie handling and crawls an authenticated site whose pages link or redirect to other hosts. In that case the session cookie of the authenticated origin is sent to those hosts. Mitigation Upgrade to 4.0.0, where a cookie without a `Domain` attribute is sent only to the host that set it, a single-label domain is rejected and the domain check fails closed. Because the protocol does not yet record the host that issued a cookie, cookies without a `Domain` attribute are not sent at all until that host is recorded; operators relying on cookie transfer will notice this. The documentation error is corrected in the same release. Users who cannot upgrade immediately should confine an authenticated crawl to a topology whose URL filters keep it on the origin that issued the credentials, and should not rely on cookie scoping as a boundary. Rotating session credentials used for such crawls is advisable. Credit Independently reported to the Apache StormCrawler PMC by n0mi1k, with a proof of concept. Also found by the ASF -- using Claude agents to study the security of open-source projects, validated and reported by Apache StormCrawler.

CVE-2026-82442

Published: 2026-11-24 05:17:20 CDT

Severity: N/A

CVSS Score: N/A

Description `HostURLFilter.configure` reads the `ignoreOutsideDomain` parameter but tests the node belonging to `ignoreOutsideHost` when deciding whether the domain mode was configured. A filter configuration that names only `ignoreOutsideDomain`, which the class documentation presents as an independent mode, is therefore discarded: the flag is forced to false, `filter` short-circuits on its guard and every URL is returned unchanged. The filter enforces nothing while appearing to be configured, and the failure is silent. The mirror-image configuration, naming only `ignoreOutsideHost`, fails with a `NullPointerException` while the topology is starting. The effect is the loss of a scope control the operator configured, so a crawled page's outlinks are followed to hosts the operator intended to exclude. Impact beyond crawl scope depends on what the crawler then fetches and is not claimed here. Projects generated from the StormCrawler Maven archetypes are not affected, because all three shipped filter configurations set both parameters. Mitigation Upgrade to 4.0.0, where each parameter is tested independently. Operators whose configuration sets only `ignoreOutsideDomain` will find the crawl restricted to the source domain, as configured, which may reduce the number of outlinks accepted. Users who cannot upgrade immediately should set both `ignoreOutsideHost` and `ignoreOutsideDomain` explicitly in the `HostURLFilter` configuration, which produces the intended behaviour on affected versions. CVE-2026-59415

Published: 2026-11-24 05:17:20 CDT

Severity: CRITICAL

CVSS Score: 10.0

TypesenseVectorStore is vulnerable to a document ID injection in its delete operation that can cause unintended documents to be deleted. TypesenseVectorStore.doDelete(List) builds a Typesense filter_by expression by raw string concatenation of caller-supplied document IDs into the form id: [id1,id2,...] . The Typesense id field uses bare (unquoted) values in this list form with no escaping mechanism. An ID containing characters with syntactic meaning in the Typesense filter grammar — such as a comma ( , ), a closing bracket ( ] ), or operator tokens ( || , && ) — can break out of the list literal and alter the structure of the filter expression. An attacker who controls a document ID passed to the delete operation can use this to delete documents other than the intended ones (comma injection), or to construct a filter that matches every document in the collection (operator breakout), resulting in unintended bulk deletion. Applications that pass externally supplied or user-controlled document IDs to VectorStore.delete(List) backed by TypesenseVectorStore are affected.
