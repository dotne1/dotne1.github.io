CVE-2026-90592

Published: 2026-11-25 15:17:20 CDT

Severity: MEDIUM

CVSS Score: 4.6

The ITE it51xxx I2C driver, when operating as an I2C target (slave) in buffer mode (CONFIG_I2C_TARGET + CONFIG_I2C_TARGET_BUFFER_MODE), transmits response data from the fixed-size data->target_out_buffer inside its target FIFO interrupt handler target_i2c_isr_fifo() in drivers/i2c/i2c_ite_it51xxx.c. On every data interrupt of a host read transaction the handler pushes a fixed 16 bytes from target_out_buffer[i + data->r_index] into the hardware FIFO and then advances data->r_index by 16, without ever checking that index against the size of the buffer. data->r_index is reset to zero only on a STOP or timeout condition, so within a single transaction it only accumulates. An I2C host that keeps clocking read bytes without issuing STOP drives data->r_index past the end of the buffer after sixteen interrupts (default CONFIG_I2C_TARGET_IT51XXX_MAX_BUF_SIZE = 256 bytes), and every interrupt after that reads 16 bytes from beyond target_out_buffer and places them on the bus. What follows the buffer in the driver's device data structure is data->target_shared_fifo and the remaining static device state, so a sufficiently long read transaction streams adjacent firmware memory to the host. The same handler, and the shared-FIFO arm of target_i2c_isr_pio(), also declare the transfer length uninitialised and invoke the optional buf_read_requested() callback without checking that it is registered. A target that supplies no read callback leaves the source pointer NULL and the length indeterminate; when that length compares below the destination size, memcpy() runs with a NULL source. Because the transmit path feeds the FIFO whether or not the callback provided data, such a target also places whatever the previous request left in the buffer onto the bus. The trigger is a malicious or misbehaving I2C master on the same bus (for example a compromised application processor or a rogue device on an exposed I2C bus); no software privilege on the victim is required and the handler runs in the target's kernel/firmware context. The disclosed bytes are not attacker-chosen, but their extent is: the host controls how long the transaction runs and therefore how far past the buffer the driver reads. This is the read-direction counterpart of CVE-2026-14986, which closed the write direction of the same routine without adding the matching bound on the read path.

CVE-2026-102960

Published: 2026-11-25 15:17:16 CDT

Severity: MEDIUM

CVSS Score: 6.8

The Grow R502-A fingerprint sensor driver (drivers/sensor/grow_r502a/grow_r502a.c) receives sensor responses in the UART interrupt handler uart_cb_handler(). Once the 9-byte header has arrived, the handler reads the 16-bit package length from the header and uses it as the byte count for further uart_fifo_read() calls into rx_buf.data. It never checks that length against the destination buffer. That buffer is a union r502a_packet on the calling thread's stack, set up by transceive_packet(), and is only CONFIG_R502A_DATA_PKT_SIZE + 12 bytes long (140 bytes by default). A malicious or counterfeit sensor module, or an attacker who tampers with the UART wiring, can reply to any driver command with a header that declares a length of up to 65535 bytes. The ISR then writes that many attacker-supplied bytes past the end of the stack buffer. The existing length check in r502a_validate_rx_packet() runs only after the data has been written, so it does not prevent the overflow. Every sensor transaction is affected, including the ones issued by fps_init() during device initialization. The result is a stack overwrite with attacker-controlled length and content in the calling thread. This can corrupt control data and may lead to arbitrary code execution on the host MCU, which would undermine any function the fingerprint sensor is meant to protect. The fix validates the declared length against CONFIG_R502A_DATA_PKT_SIZE as soon as the header is complete and aborts the reception if it is out of range.

CVE-2026-102959

Published: 2026-11-25 15:17:15 CDT

Severity: MEDIUM

CVSS Score: 6.4

The Grow R502-A fingerprint sensor driver (drivers/sensor/grow_r502a/grow_r502a.c) points drv_data->rx_buf.data at an rx_packet buffer on the caller's stack and enables the UART RX interrupt before waiting 1500 ms for a reply. When the wait timed out, transceive_packet() returned -ETIMEDOUT but left the RX interrupt enabled and rx_buf.data still pointing at the caller's buffer. Once the caller's frame has returned, any bytes that arrive late on the UART are written by the interrupt handler uart_cb_handler() through the dangling pointer into stack memory that the thread has since reused. The bytes come from the device on the other end of the UART. An attacker with physical access who replaces or impersonates the fingerprint module can trigger this by delaying a reply past the timeout and then sending a packet. A slow or faulty genuine module can also trigger it by accident. The result is a write of attacker-chosen bytes into a live thread stack. The write length comes from the header of the late packet. Commit 96968fac22b, which landed together with this fix, bounds it to a header plus CONFIG_R502A_DATA_PKT_SIZE bytes; affected releases do not have that bound. This can crash the device and may allow control-flow hijacking, depending on what occupies the reused stack region. The fix disables the RX interrupt, resets the RX semaphore and clears rx_buf.data on timeout, and the interrupt handler now refuses to write when no receive buffer is armed.

CVE-2026-102957

Published: 2026-11-25 15:17:15 CDT

Severity: HIGH

CVSS Score: 7.7

z_impl_pwm_capture_cycles() in drivers/pwm/pwm_capture.c stores its capture context (struct z_pwm_capture_cb_data, including a struct k_sem) on its own stack and registers a pointer to it as the driver capture callback's user_data. When called with a K_NO_WAIT timeout, k_sem_take() returns -EBUSY, which the function did not handle: it fell through, returned the uninitialized status field, copied uninitialized period/pulse values to the caller when that status happened to be zero, and returned without disabling the capture or clearing the callback. pwm_capture_cycles() is a system call, and z_vrfy_pwm_capture_cycles() passes the caller's timeout through unchanged. With CONFIG_USERSPACE and CONFIG_PWM_CAPTURE enabled, an unprivileged user-mode thread that has been granted access to a capture-capable PWM device can pass K_NO_WAIT to trigger the defect. Without userspace the function is only reachable from trusted application code. The uninitialized values come from the thread's privileged (kernel) stack, so a user-mode caller can read up to 8 bytes of stale kernel stack memory per call. More seriously, when the capture later completes, the driver ISR invokes z_pwm_capture_cycles_callback() with the dangling pointer. The callback writes into the expired kernel stack region and calls k_sem_give() on whatever memory now occupies it, which can corrupt live kernel stack frames and make the scheduler walk a forged wait queue. The result is kernel memory corruption from interrupt context, leading at least to a crash and possibly to privilege escalation out of the userspace sandbox. The fix rejects K_NO_WAIT with -EINVAL before any capture is configured.
