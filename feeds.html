CVE-2026-102956

Published: 2026-11-23 13:17:28 CDT

Severity: LOW

CVSS Score: 3.1

ethernet_send() in subsys/net/l2/ethernet/ethernet.c dropped the caller's reference on an IPv4 packet whenever net_arp_prepare() returned NET_ARP_PKT_REPLACED. That return value is also used when ARP could not queue the packet because every ARP cache entry is already pending. In that case ARP holds no reference of its own, so the original packet was freed before the replacing ARP request was transmitted. If transmitting the ARP request then failed (a driver send error or an ethernet_fill_header() failure), the error path called net_pkt_ref() on the freed packet. net_if_tx() then called net_pkt_unref() on it again. If the freed net_pkt slab slot was reallocated in between, the stray unref releases a reference owned by an unrelated packet, which is freed while still in use. An attacker on the local link can drive the ARP cache into the all-pending state. CONFIG_NET_ARP_TABLE_SIZE defaults to 2, so it is enough to elicit replies to a few spoofed, non-responding on-subnet addresses. Reaching the memory corruption also needs a transmit failure the attacker does not directly control and a narrow slab-reuse race. The practical impact is corruption or a crash of the network stack (denial of service).

CVE-2026-102955

Published: 2026-11-23 13:17:28 CDT

Severity: LOW

CVSS Score: 3.1

The OpenThread PSA crypto platform backend in modules/openthread/platform/crypto_psa.c only supported PSA key references. otPlatCryptoAesSetKey() copied aKey->mKeyRef into the AES context unconditionally. On an OpenThread Radio Co-Processor (RCP) build, CONFIG_OPENTHREAD_CRYPTO_PSA does not select CONFIG_OPENTHREAD_PLATFORM_KEY_REF, so OpenThread passes the MAC key as literal bytes and mKeyRef is uninitialized. psa_cipher_encrypt() in otPlatCryptoAesEncrypt() then fails without writing its output, and the error is only caught by an OpenThread assertion that is compiled to a no-op when CONFIG_ASSERT is disabled. When the RCP handles transmit security in software, AES-CCM* is never keyed. That is the case with Thread 1.2 or later, where CONFIG_OPENTHREAD_MAC_SOFTWARE_TX_SECURITY_ENABLE defaults to y, on a radio driver without IEEE802154_HW_TX_SEC. Every MAC key-id-mode-1 frame goes out with its payload XORed against a single 16-byte pad of stale stack data, reused for every block, and with an unkeyed MIC. CONFIG_OPENTHREAD_CRYPTO_PSA is enabled by default since v4.4.0. A passive attacker within 802.15.4 radio range can recover the pad from predictable plaintext (for example 6LoWPAN headers) and read the payload of the frames the device transmits. The practical impact is limited. The configuration is not the default (the default Thread version is 1.1), and the same defect makes peers reject every secured data frame, so an affected device cannot exchange data on the network. Received traffic and key distribution are not affected. With CONFIG_ASSERT enabled, the RCP halts on the first secured transmission instead.

CVE-2026-102954

Published: 2026-11-23 13:17:28 CDT

Severity: MEDIUM

CVSS Score: 6.8

The STM32 SMBus driver (drivers/smbus/smbus_stm32.c) implements smbus_block_read() and smbus_block_pcall() by issuing a single i2c_transfer() in which the byte-count byte returned by the peripheral is read directly into the len field of the following i2c_msg. That message then receives data straight into the caller-supplied buffer. Nothing bounds the count, so smbus_stm32_block_read() and smbus_stm32_block_pcall() read up to 255 bytes into a buffer that the SMBus API documents (and the syscall verifiers validate) as holding at most SMBUS_BLOCK_BYTES_MAX (32) bytes. The count is chosen by the addressed SMBus peripheral. A malicious, counterfeit or faulty device on the bus (for example a removable smart battery, PMBus supply or plug-in module), or anyone able to drive the bus lines, can report a block count above 32 and cause the driver to write up to 223 bytes past the end of the caller's buffer. Callers typically pass a 32-byte stack buffer, as the in-tree smbus block_read shell command does, so the overflow lands on the caller's stack before any caller-side count check can run. The result is attacker-controlled stack or memory corruption in the context of the calling thread, which can crash the system or potentially be leveraged for code execution. When the call arrives through the smbus_block_read/smbus_block_pcall system calls, the out-of-bounds write happens in supervisor mode beyond the 32-byte region validated for the user thread. The fix receives the block into a driver-local 255-byte buffer and copies it out only when the count is at most SMBUS_BLOCK_BYTES_MAX, returning -ENODATA otherwise.

CVE-2026-102953

Published: 2026-11-23 13:17:28 CDT

Severity: MEDIUM

CVSS Score: 6.0

usbh_req_setup() in subsys/usb/host/usbh_ch9.c returns -ETIMEDOUT as soon as a control request times out, even though the transfer is still in flight. usbh_xfer_dequeue() only requests cancellation, and the host controller driver keeps the transfer and its data buffer until it returns it through the completion callback. Callers such as usbh_req_desc_dev() and usbh_req_desc_cfg() free the buffer (net_buf_unref()) right after usbh_req_setup() returns. Separately, a single global semaphore (ch9_req_sync) with no mutual exclusion lets a late or foreign completion wake the wrong waiter. That waiter then returns early and its caller frees a buffer the controller is still filling. A malicious USB device attached to a Zephyr USB host port can trigger this during enumeration. It NAKs a GET_DESCRIPTOR request until the 5-second timeout expires, then answers with data around the cancellation, or delays its answer to the next request after leaving a stale semaphore signal. The controller driver (for example the MAX3421E max3421e_hrslt_success() path) then writes device-controlled bytes into the freed net_buf and updates its length. The result is a use-after-free write into the USB host buffer pool with attacker-chosen contents, which can corrupt buffers that have been reallocated to other transfers, plus a leak of transfer objects. Crashes or memory corruption follow. The fix serializes usbh_req_setup() with a mutex, resets the semaphore before each request, and waits for the driver to return a cancelled transfer before freeing it. Only builds with the experimental CONFIG_USB_HOST_STACK are affected.

CVE-2026-102952

Published: 2026-11-23 13:17:28 CDT

Severity: MEDIUM

CVSS Score: 4.8

The Zephyr TFTP client in subsys/net/lib/tftp/tftp_client.c does not check where the reply to its request comes from. After sending a read or write request to the configured server, send_request() accepts the first UDP datagram that arrives on the client's socket from any address and port. It then calls zsock_connect() to that sender, so the sender becomes the peer for the rest of the transfer. RFC 1350 requires a client to discard datagrams whose source does not match the transfer ID it expects. A host that can send a UDP datagram to the client's ephemeral port before the real server replies can take over the transfer. It can reply from its own address and does not need to spoof the server. A host on the same network segment that sees the request can do this easily. An off-path attacker must guess the randomized ephemeral port and win the race, which is easier when the server is slow or unreachable. No authentication or user interaction is needed beyond the device starting a transfer through tftp_get() or tftp_put(), for example from an application or the net tftp shell command. For tftp_get(), the attacker chooses the entire content handed to the application's data callback. For tftp_put(), the whole upload buffer is sent to the attacker. There is no memory corruption. TFTP itself has no authentication, and after the fix an attacker who can spoof the server's IP address can still interfere with a transfer. The fix checks the server's address on the first reply and the full address and port on every later datagram, and drops mismatches without using up the transfer's retries.

CVE-2026-102951

Published: 2026-11-23 13:17:28 CDT

Severity: MEDIUM

CVSS Score: 6.6

The Intel SoC FPGA Agilex5 SoC's static MMU region table in soc/intel/intel_socfpga/agilex5/mmu_regions.c mapped the System Manager peripheral (sysmgr) with MT_P_RW_U_RW. That sets the EL0 access-permission bit in the page-table descriptor, so user mode can read and write the block. The other peripheral windows in the same table, and the same block on the sibling Agilex SoC, are correctly mapped MT_P_RW_U_NA. On arm64, memory-domain page tables are cloned from the kernel page tables (arch_mem_domain_init()). When CONFIG_USERSPACE is enabled, every user mode thread therefore gets direct load/store access to the System Manager registers, with no partition grant or system call. Any untrusted code running as a user thread can exploit this. The System Manager controls system-wide state that only the kernel should own: NoC/FPGA-bridge idle requests, SDMMC and EMAC interface configuration, FPGA interface enables and boot scratch registers. A user thread can stall the interconnect or reconfigure peripherals out from under kernel drivers, causing denial of service and integrity loss for the platform, and can read that configuration. This breaks the userspace isolation boundary. Builds without CONFIG_USERSPACE (the default) are not affected. The fix maps the region MT_P_RW_U_NA.

CVE-2026-102950

Published: 2026-11-23 13:17:28 CDT

Severity: MEDIUM

CVSS Score: 5.9

The mount-time recovery scan of the Zephyr Memory Storage (ZMS) key-value store, zms_recover_last_ate() in subsys/kvss/zms/zms.c (subsys/fs/zms/zms.c in older releases), computes the end of the sector's data area incorrectly. Every valid allocation table entry (ATE) reset the data-end bound to the start of the sector, including entries whose value is stored inline (8 bytes or less) and delete entries. When the newest ATE in the active sector is one of these, the scan continues past the ATE area into the payload area and reads stored value bytes as struct zms_ate records. Any payload slot that passes the ATE check (a CRC8 plus the one-byte sector cycle count) is adopted as the newest entry. zms_init() then sets fs->ate_wra and fs->data_wra from it. The pointers are only this weak check away from data an application may have stored on behalf of a remote party: a BLE-writable device name, provisioned credentials, or configuration received over the network. An attacker who can get about 16 bytes of chosen content persisted in a ZMS value can plant a forged ATE. The forged entry takes effect after the next mount, provided the newest entry in that sector is small or a delete. Random data can also match by chance, which is how the issue was found. A forged or accidentally matched ATE overrides the stored entry for any chosen id. Its inline data or its offset/len pointer controls what later reads of that key return. The misplaced write pointers also make later writes place ATEs and payloads over other entries' existing data, silently corrupting persistent configuration such as settings values stored in ZMS. The effects are limited to the active flash sector and to what ZMS returns to its callers. No RAM out-of-bounds access was identified.

CVE-2026-102949

Published: 2026-11-23 13:17:27 CDT

Severity: MEDIUM

CVSS Score: 6.4

The Intel SEDI I2C controller driver (drivers/i2c/i2c_sedi.c, used on Intel ISH platforms) waits for each asynchronous transfer with k_sem_take() on a per-controller completion semaphore and a 1 s timeout. When the wait times out, i2c_sedi_api_full_io() aborts the transfer via SEDI_I2C_ABORT_TRANSFER, but if the controller's completion interrupt fires between the timeout expiring and the abort masking interrupts, the callback k_sem_give()s the semaphore and the token is never discarded. The next transfer on that bus then takes the stale token immediately and returns success (the stale context->err is usually 0) while the controller is still executing it. The HAL interrupt handler (or DMA) keeps copying received bytes into the caller's msgs[i].buf. Since I2C callers typically pass stack buffers, this writes into a stack frame that has already been returned from, and the caller also consumes incomplete data. The desynchronization can persist across later transfers. Triggering the race requires a transfer to complete just after the 1 s timeout. A device on the I2C bus that controls clock stretching (for example a malicious or tampered peripheral) can steer this timing, and it also supplies the bytes that get written. Exploitation therefore needs physical access to the bus and is timing-dependent. The impact is corruption of kernel or thread stack memory with data the peripheral controls, which can lead to a crash or potentially to code execution. The fix calls k_sem_reset() and clears context->err after the abort, while the transfer mutex is still held.

CVE-2026-102948

Published: 2026-11-23 13:17:27 CDT

Severity: MEDIUM

CVSS Score: 5.3

Several Bluetooth LE Audio services in subsys/bluetooth/audio register global connection and authentication callbacks but assume every connection is LE. When CONFIG_BT_CLASSIC is enabled, the host also invokes these callbacks for BR/EDR connections. For such connections bt_conn_get_dst() returns NULL, and bt_conn_get_info() leaves info.le.dst unset (zero or uninitialized stack data). The CSIP Set Member (csip_disconnected(), handle_csip_disconnect(), handle_csip_auth_complete()), PACS (pacs_auth_pairing_complete(), pacs_security_changed()) and HAS (security_changed(), client_alloc(), client_free()) callbacks then compare or copy a Bluetooth address through that NULL or uninitialized pointer. A remote device within Bluetooth range can trigger this against a dual-mode device that exposes LE Audio server roles and accepts BR/EDR connections. Opening and closing a BR/EDR ACL link, with no pairing, reaches the CSIP Set Member disconnect path. Completing SSP pairing (for example Just Works) or encryption reaches the PACS and HAS paths. The impact is denial of service. With CONFIG_ASSERT enabled, the device halts on an assertion (bt_keys_find_addr(), context_alloc()). On platforms that trap NULL or wild reads, it crashes. Otherwise, internal PACS/CSIP/HAS client state is corrupted with bogus addresses. The defects are reads only, and the attacker does not control the address that is dereferenced. The fix adds bt_conn_is_type(conn, BT_CONN_TYPE_LE) checks at the top of the affected callbacks.
