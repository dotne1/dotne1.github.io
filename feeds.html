CVE-2026-8748

Published: 2026-11-25 17:17:26 CDT

Severity: N/A

CVSS Score: N/A

Crypt::JWT versions before 0.037_1 for Perl compare HMAC signatures and JWE authentication tags in non-constant time. decode_jwt compares HS256, HS384 and HS512 signatures, and the authentication tag of A128CBC-HS256, A192CBC-HS384 and A256CBC-HS512 encrypted tokens, against the computed value with Perl's eq operator. CVE-2026-136795

CVSS Score: N/A

Crypt::JWT versions before 0.037_1 for Perl allow memory exhaustion via unbounded inflation of zip DEF payloads. When a token header sets "zip" to "DEF", decode_jwt inflates the payload with no limit on the output size. A signed token is inflated after its signature verifies. CVE-2026-136515

Published: 2026-11-25 17:17:24 CDT

Severity: HIGH

CVSS Score: 7.5

psqlODBC rewrites statement text for keyset-driven cursors and ODBC escapes using positions it found in the text. These positions could lie outside the text or describe another statement: - After SQLExecDirect() failed on a statement handle, the FROM and WHERE positions of the failed statement were applied to the next, shorter statement on that handle. - The parser could record a FROM position with no text after it, and the rewrite then copied a negative length. - An {fn …} escape whose arguments contain FOR UPDATE, ; or INTO … FROM made the driver remove a cursor prefix from the wrong buffer. - {fn CONVERT(?, …)} with an output parameter produced a negative argument length. - An unclosed {fn …} escape made the driver read past the statement, and a few thousand nested ones exhausted the stack. - Translating @@identity in long statement text read an uninitialised pointer, and {? = call …} with nothing bound for the return value dereferenced NULL. Whoever supplies the text of a statement that an application opens on a keyset-driven or dynamic cursor with a concurrency other than read-only, or calls with an output parameter, can corrupt the application's heap and end it. That includes the users of query tools, report builders and other applications that run SQL their users type. Code execution has not been demonstrated. Versions up to and including psqlODBC 18.00.0006 are affected.

CVE-2026-136514

Published: 2026-11-25 17:17:24 CDT

Severity: MEDIUM

CVSS Score: 6.5

psqlODBC assumed that a table it reads keeps the definition it had when the statement was described or parsed. A database user who owns a table or view another user's application reads can crash that application, with an honest server and default options, in these cases: - Columns dropped or added in another session while the application updates rows through an updatable cursor, or describes the columns with Parse=1. - A view whose ctid is NULL, read through an updatable cursor, which writes past the row cache, and a view with a volatile filter scrolled backward with UseDeclareFetch=1. - Rows added through an updatable cursor to a table with child tables or partitions. - A column whose type is named lo, written with data-at-execution parameters. - A DROP TABLE or ALTER TABLE on the connection while another statement still uses the table's column information. - NULL key columns in rows the driver re-reads for an updatable cursor. - A function called with more output parameters than its result has columns. - SQLTables() and SQLTablesW() dereferenced NULL when called with empty strings for the catalog, schema and table names together with a NULL TableType, which kills the process that loaded the driver and every session it serves. The demonstrated results are crashes; one case writes past a heap buffer, but code execution has not been demonstrated. Versions up to and including psqlODBC 18.00.0006 are affected.

CVE-2026-136512

Published: 2026-11-25 17:17:24 CDT

Severity: HIGH

CVSS Score: 7.5

With SQL_C_DEFAULT, the C type of a bound column or parameter follows its SQL type. An application sizes its buffer from the type it was told when it described the statement. When the column had another type at fetch time, because the server reported another type, the table was altered, or an output parameter's result column had another type, psqlODBC wrote the larger type into the smaller buffer: 12 bytes past a 4-byte buffer for a uuid, and more in multi-row fetches, where the driver also steps through the array by the larger size. Other conversions wrote past the application's buffer as well: - With Int8As set to a smaller type, an int8 column fetched as SQL_C_DEFAULT was still written as 8 bytes. - An int2vector column fetched as SQL_C_DEFAULT returned unterminated binary data instead of text. - An output parameter that the application discards by binding a NULL buffer overflowed a stack buffer in the driver. - SQLGetData() with BufferLength 0 on a column the driver reads as a large object wrote a NUL byte past the buffer. - Adding a row with SQLBulkOperations(SQL_ADD) on a static updatable cursor before the first fetch, then changing that row, rolling back and fetching it, made the keyset index arithmetic free a pointer that was never allocated and corrupt the heap. This can be triggered by a hostile or compromised server, or anyone on the network path of a connection that does not use sslmode=verify-full (the default is disable), and by the owner of a table the application reads. Versions up to and including psqlODBC 18.00.0006 are affected.

CVE-2026-136510

Published: 2026-11-25 17:17:24 CDT

Severity: MEDIUM

CVSS Score: 4.8

A parameter-array execution that fails part-way leaves the rows it has already queued on the statement handle, and the next execution on that handle sends them. After a data-at-execution batch is abandoned, by SQLCancel or a rejected SQLPutData, the next SQLExecDirect sends the failed batch's rows and returns SQL_SUCCESS without sending its own statement. So an application that logs the failure on the same handle has its log entry turned into a silent no-op, while rows it was told had failed are stored. An end user who controls one value in an application's array insert can arrange both halves of that. A second route needs no data-at-execution parameter: when building a later row fails in parameter conversion, the queued rows go to the server ahead of the next parameter array on the handle, inside whatever transaction and session settings are current by then. One variant also writes past the end of a shorter SQL_ATTR_PARAM_STATUS_PTR array supplied by the next statement. The statements that run are the application's own, correctly quoted; no SQL text comes from outside. Versions from psqlODBC 12.02.0000, which introduced batched parameter-array execution, up to and including 18.00.0006 are affected.

CVE-2026-136509

Published: 2026-11-25 17:17:24 CDT

Severity: HIGH

CVSS Score: 7.5

psqlODBC did not check that a server reply matches the query it sent: that a FETCH returns no more rows than it asked for, that each row has the described number of columns, that one query produces one result, and that a COPY, a transaction or the connection ends where the protocol says. By sending replies that do not match, a hostile or compromised server, or anyone on the network path of a connection that does not use sslmode=verify-full (the default is disable) can corrupt memory in the application: - A FETCH reply with more rows than requested overflows the row cache. - Extra results in reply to a FETCH, or to the queries of a keyset-driven cursor, are freed while still in use. - A key query of a keyset-driven cursor answered with extra columns, or a re-read row with fewer columns, overflows the row cache. - Replies without columns or rows, or with NULL values, to the driver's internal queries at connect time and in catalog functions are dereferenced. - A malformed relacl value in SQLTablePrivileges() makes the driver write past a buffer. - On Windows with MSDTC, a long transaction name returned by the server overflows a buffer during recovery. - Values in replies to the driver's internal queries are used without checking their range: an empty column name, a parameter count, a large-object size, a function's or trigger's argument count, and a result of exactly 32767 columns. They are dereferenced, read past, returned to the application or sent back to the server as stack memory, or make the driver loop forever. - A reply that ends a COPY, the connection or the transaction at an unexpected point leaves freed results, keysets or table information in use: a CopyOutResponse followed by a lost connection, a ROLLBACK command tag under UseDeclareFetch=1, or a lost connection while a cursor with positioned updates is closed. Eight extra bytes in a reply also make the driver wait forever for a COPY to end. - On Windows, a start-up reply without client_encoding crashes the driver, and with MSDTC a failed connection makes the XA library use a connection it has already freed. - An error message ending in the first byte of a multibyte character leaves the SQLSTATE returned by SQLGetDiagRecW() unterminated. - When a string value did not fit the application's buffer, eight Unicode entry points filled the buffer and wrote no null terminator, so a caller that reads to the terminator, as ODBC allows, read past the end of its own buffer. This continues the fixes for CVE-2026-120058 and CVE-2026-120060, which covered other replies. The demonstrated results are crashes and heap corruption; code execution has not been demonstrated. Versions up to and including psqlODBC 18.00.0006 are affected.

CVE-2026-136508

Published: 2026-11-25 17:17:23 CDT

Severity: MEDIUM

CVSS Score: 6.8

On Windows, when a connection takes part in a distributed transaction, psqlODBC and its XA library open further connections of their own to finish the transaction. These connections did not keep the security settings of the application's connection: - When the XA library's first connection attempt failed, it tried again with sslmode=allow, even for a data source configured with sslmode=verify-full or verify-ca. - The connections the driver opens itself ignored every libpq option given through pqopt, such as channel_binding=require, and the open string it registers with MSDTC carried no pqopt, so the XA library's connections dropped those options too. An attacker on the network path between the MSDTC host and the PostgreSQL server, without a certificate or credentials, can make those connections go to a server of their choosing without TLS, read and change what they send, and decide the outcome MSDTC records for the transaction. Versions up to and including psqlODBC 18.00.0006 are affected.

CVE-2026-136507

Published: 2026-11-25 17:17:23 CDT

Severity: HIGH

CVSS Score: 8.1

psqlODBC parsed and built connection strings in ways that let a value end early: - In a braced value, such as PWD={…}, a trailing byte 0x7d of a GBK, Big5 or SJIS character was taken for the closing brace. - A braced value that ended right after an escaped }} was not reported as unterminated, and its contents were parsed as further keywords. - SQLConnectW(), SQLDriverConnectW() and SQLBrowseConnectW() cut a connection string whose UTF-8 form is longer than 32767 bytes, which changes how the rest of it is parsed. - On Windows with MSDTC, the password and user name were put into the XA open string without escaping, and the XA library copied each item of that string into a 64-byte stack buffer. - Percent-encoding a long password wrote one byte past a 4096-byte stack buffer. An end user who supplies a password, or another value the application puts into the connection string, can set other connection keywords, for example to connect the application to a server of their choosing. The MSDTC case can also overflow a stack buffer in the process that loads the XA library. Versions up to and including psqlODBC 18.00.0006 are affected.
