CVE-2026-84785

Published: 2026-11-24 06:17:25 CDT

Severity: N/A

CVSS Score: N/A

Issue summary: A QUIC peer that sends many small out-of-order STREAM fragments while withholding the first byte of the stream may cause OpenSSL to buffer a large number of reassembly nodes occupying much larger memory than the actual data sent. Impact summary: A remote peer can pin large amounts of memory on a server that accepts incoming QUIC streams, potentially exhausting memory and causing Denial of Service. CWE: CWE-770: Allocation of Resources Without Limits or Throttling Description: QUIC receive flow control limits the highest byte offset a peer may reach on a stream. It does not limit how many out-of-order fragments the receiver buffers. OpenSSL allocates a reassembly node for each non-adjacent STREAM fragment and never caps the count. A peer that opens a stream and sends many one-byte fragments at increasing offsets, while withholding the first byte, makes the receiver retain one node per fragment without delivering any data. Only applications that accept incoming streams are exposed. With the default policy, which rejects peer-initiated streams, the stream is torn down before state accumulates. Because the read side never advances past the missing prefix, the flow control window never slides and the nodes stay pinned for the life of the connection. The per-stream window bounds the highest offset, so the memory one stream can pin is finite, but it can reach tens of megabytes and, across many streams and connections, drive memory pressure and Denial of Service. The severity is limited because the exhaustion is bounded by flow control and requires a non-default configuration. FIPS impact: no The affected code is outside the FIPS module boundary.

CVE-2026-62269

Published: 2026-11-24 06:17:25 CDT

Severity: N/A

CVSS Score: N/A

Improper Encoding or Escaping of Output vulnerability in ex_aws (S3 request URL construction). This vulnerability is associated with program files lib/ex_aws/request/url.ex and program routines ExAws.Request.Url.build/2, ExAws.Request.Url.sanitize/2 and ExAws.Request.Url.get_path/2. ex_aws does not percent-encode reserved characters in S3 object keys when it assembles the request URL. A literal ? in an object key survives unencoded: build/2 inserts the operation path verbatim and URI.to_string/1 emits it without encoding, and sanitize/2 then splits the flattened URL on the first ?, treating everything after it as the query string. Because the split runs before uri_encode is applied to the path, the ? is never neutralized, and the recovered query is re-inserted without any encoding. An attacker who controls part of an object key (for example a download or upload keyed by a user-supplied filename) can therefore truncate the key past application-appended suffixes, causing the request to address a different object than the application intended, and can inject live S3 sub-resource operations (such as ?acl, ?tagging or ?versions) into the request. The manipulated URL is signed and transmitted normally, so the tampering is authorized like any legitimate request. This issue affects ex_aws: from 2.1.2 before 2.8.0.

CVE-2026-59698

Published: 2026-11-24 06:17:24 CDT

Severity: N/A

CVSS Score: N/A

Relative path traversal in ex_aws allows an attacker who controls an S3 object key to escape the intended bucket or key prefix. When ex_aws builds a path-style S3 request, ExAws.Operation.S3.add_bucket_to_path/2 in lib/ex_aws/operation/s3.ex joins the bucket name and the object key into a single path string and then normalizes it, collapsing . and .. segments the way a filesystem path would. Because the bucket is the first segment of the combined string, a leading ../ in the object key pops the bucket off the path. With bucket mybucket and a key of ../victim/secret.txt, the combined /mybucket/../victim/secret.txt normalizes to /victim/secret.txt, so the request (signed with the application's own credentials) is sent to bucket victim. The same mechanism collapses ../ within a key, defeating any isolation an application enforces by prepending a trusted prefix. Only the default path-style configuration is affected; requests built with virtual_host: true do not run this normalization. Because S3 treats object keys as opaque and does not resolve .. itself, the client-side normalization introduces a traversal that would not otherwise exist. Any application that derives an S3 object key from untrusted input and relies on the bucket, or a key prefix, as a tenant or trust boundary is exposed to cross-bucket or cross-prefix read and write, depending on the operation and the credentials' permissions. This issue affects ex_aws: from 2.1.7 before 2.8.0.

CVE-2026-59697

Published: 2026-11-24 06:17:24 CDT

Severity: N/A

CVSS Score: N/A

Server-Side Request Forgery (SSRF) vulnerability in ex_aws (instance metadata token provider). This vulnerability is associated with program files lib/ex_aws/instance_meta_token_provider.ex and program routines ExAws.InstanceMetaTokenProvider.request_token/1 and ExAws.InstanceMetaTokenProvider.get/1. ex_aws requests its IMDSv2 session token from the link-local metadata endpoint (http://169.254.169.254/latest/api/token) with HTTP redirect following enabled. Because the token request follows 3xx redirects and does not restrict the redirect target to the link-local range, an attacker who can influence the response to the metadata request (for example an on-segment neighbor spoofing the link-local address) can answer with a redirect to an arbitrary host. The library follows the redirect and accepts the arbitrary host's response body as the IMDSv2 session token, caching it and sending it as the x-aws-ec2-metadata-token header on every subsequent metadata and credential request. This issue affects ex_aws: from 2.3.0 before 2.8.0.
