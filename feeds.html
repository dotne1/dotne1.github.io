CVSS Score: N/A

Allocation of resources without limits or throttling vulnerability in Apache SkyWalking BanyanDB. Uncontrolled resource consumption in Apache SkyWalking BanyanDB's query API allows a remote unauthenticated attacker to cause the server to exhaust memory and terminate. A query request can specify an arbitrarily large result limit and offset, which the server uses to pre-allocate result buffers without an upper bound; a single request may force an allocation of tens of gigabytes and cause the process to be killed This issue affects Apache SkyWalking BanyanDB: from 0.11.0 before 0.11.1. CVE-2026-62272

Published: 2026-11-26 07:16:45 CDT

Severity: N/A

CVSS Score: N/A

Relative Path Traversal vulnerability in ex-aws ex_aws_lambda (ExAws.Lambda module) allows an attacker to redirect an AWS Lambda control-plane request at an unintended resource by injecting path traversal sequences into a caller-supplied identifier. This vulnerability is associated with program file lib/ex_aws/lambda.ex and program routines ExAws.Lambda.add_permission/5, ExAws.Lambda.delete_event_source_mapping/1, ExAws.Lambda.delete_function/1, ExAws.Lambda.get_event_source_mapping/1, ExAws.Lambda.get_function/1, ExAws.Lambda.get_function_configuration/1, ExAws.Lambda.get_policy/1, ExAws.Lambda.invoke/4, ExAws.Lambda.invoke_async/2, ExAws.Lambda.remove_permission/2, ExAws.Lambda.update_event_source_mapping/2, ExAws.Lambda.update_function_code/2, ExAws.Lambda.update_function_configuration/2. ExAws.Lambda builds every request path by interpolating caller-supplied identifiers (function names, ARNs, UUIDs, statement IDs) directly into the URL with plain string interpolation, without percent-encoding or validation. The shared request helper only encodes query parameters, never the path, so path metacharacters such as / and .. reach the wire unchanged. An application that passes an untrusted or user-influenced identifier into an ExAws.Lambda operation can therefore have its request steered at a different Lambda resource: a ../ segment climbs out of the intended /2015-03-31/functions/ slot and, once the .. is normalized by the HTTP client or the AWS endpoint, addresses a sibling function in the same account. The signed credentials and the HTTP method are unchanged, so the request still succeeds against the wrong resource. Affected operations include function deletion, invocation, configuration updates, and permission changes. Applications that only pass hardcoded or strictly validated identifiers are not affected. This issue affects ex_aws_lambda: from 2.0.1 before 2.2.0.

CVE-2026-135645

Published: 2026-11-26 07:16:43 CDT

Severity: MEDIUM

CVSS Score: 6.5

The Everest Forms – Contact Form, Payment Form, Quiz, Survey & Custom Form Builder with AI plugin for WordPress is vulnerable to File Deletion in all versions up to, and including, 3.6.4 This is due to the `delete_entry_files()` function gating file cleanup on a loose `preg_match('/signature_/', $meta_key)` substring check against the entry's meta-key rather than verifying the actual field type, which allows an ordinary Text field whose label begins with "Signature" to generate a qualifying meta-key such as `signature_1` — causing the attacker-controlled value submitted via `everest_forms[form_fields][]` to be stored verbatim and later passed to `wp_delete_file()`. This makes it possible for unauthenticated attackers to delete files within the `wp-content/uploads/` directory on the server, as `safe_delete_file()` enforces a realpath boundary that prevents deletion of files outside that directory such as `wp-config.php`. Exploitation requires an administrator to permanently delete the attacker's submitted entry, as the unauthenticated attacker cannot trigger the deletion themselves; the targeted file must also reside within `wp-content/uploads/`. Successful exploitation additionally requires an action by an administrator — the attacker cannot trigger the vulnerability on their own.
