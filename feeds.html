CVE-2026-133472

Published: 2026-11-26 04:17:08 CDT

Severity: MEDIUM

CVSS Score: 5.4

The CubeWP Framework plugin for WordPress is vulnerable to Privilege Escalation in all versions up to, and including, 1.1.32 This is due to the `cubewp_frontend_role_caps()` function, registered on the `user_has_cap` filter, which excludes REST API requests via a `REST_REQUEST` guard but omits a corresponding `XMLRPC_REQUEST` check, causing it to unconditionally widen capabilities for any Subscriber or Contributor on XML-RPC and admin-ajax.php request paths. This makes it possible for authenticated attackers with Subscriber-level access and above to escalate their privileges to the full Contributor role capability set — gaining `edit_posts`, `delete_posts`, and `read` — allowing them to create, edit, and delete posts through core XML-RPC methods such as `wp.newPost`. Critically, the capability widening is not scoped to CubeWP's own submission handlers but applies globally to all core capability gates on affected request paths, meaning any Subscriber account can exploit this with a single standard XML-RPC call and no CubeWP-specific interaction. Successful exploitation causes the attacker's own account to receive every capability defined for the Contributor role.

CVE-2026-131687

Published: 2026-11-26 04:17:07 CDT

Severity: MEDIUM

CVSS Score: 5.3

The ShopMagic – email automation for WordPress plugin for WordPress is vulnerable to Improper Verification of Cryptographic Signature in all versions up to, and including, 4.9.5 Although `CurrentCustomer::encode_tracking_data()` appends an md5 hash to the `shopmagic_visitor_` cookie to make it tamper-resistant, `CookiePersistence::get_tracking_data()` returns the raw `json_decode()`'d cookie value directly without computing or verifying that hash, leaving the cookie's `user_id`, `email`, and `meta` fields fully under attacker control. This makes it possible for unauthenticated attackers to forge the visitor cookie — which is predictable because its name is derived as `md5(siteurl)` from the public site URL — and submit it to the unprotected `wp_ajax_nopriv_capture_email_url` endpoint (which is registered without a nonce check or capability check) to impersonate any WordPress user including administrators in ShopMagic's customer-identity context, and to overwrite the stored profile metadata — including name, phone number, and billing address — of any existing guest record in `wp_shopmagic_guest` and `wp_shopmagic_guest_meta` via `GuestManager::save()`.

CVE-2026-131589

Published: 2026-11-26 04:17:07 CDT

Severity: HIGH

CVSS Score: 7.2

The AI Engine – MCP Server & AI Chatbot for WordPress, with Claude, ChatGPT & Gemini plugin for WordPress is vulnerable to Limited Arbitrary File Upload in all versions up to, and including, 3.9.4 via the `url` parameter of the `/mwai/v1/helpers/create_image` REST API endpoint. The vulnerability exists because the `add_image_from_url()` function applies the `get_allowed_mime_types()` extension allow-list only on the custom-filename branch; when the request omits a `filename` value, the empty-filename branch derives the stored file's extension directly from the URL basename via `sanitize_file_name()` without any MIME or extension validation, then writes the downloaded response body verbatim to the WordPress uploads directory via `file_put_contents()`. This makes it possible for authenticated attackers with Editor-level access and above to place attacker-controlled HTML, SVG, or JavaScript files into `wp-content/uploads/YYYY/MM/` under an attacker-chosen extension, enabling stored cross-site scripting against any administrator who opens the resulting attachment URL. The download routine accepts any HTTP response whose `Content-Type` header begins with `image/`, a value freely controlled by the attacker-owned origin server, meaning the written content need not be a valid image.

CVE-2026-130805

Published: 2026-11-26 04:17:07 CDT

Severity: HIGH

CVSS Score: 8.1

The Groundhogg plugin for WordPress is vulnerable to Cross-Site Request Forgery in versions up to, and including, 4.11 This is due to the Admin_Page::page() callback dispatching methods named directly by the $_REQUEST['action'] parameter via call_user_func([$this, $action]) without verifying a nonce: the only nonce check lives in process_action() (admin_init), which prefixes the action with 'process_' before dispatching, so an attacker who supplies action=process_delete causes process_action() to look up the nonexistent 'process_process_delete' method and bail without ever calling wp_verify_nonce(), while page() subsequently invokes the real process_delete() (and other process_* methods such as process_spam, process_status_change, process_edit) with no CSRF token of its own. This makes it possible for unauthenticated attackers to delete arbitrary contacts, change contact opt-in status (including marking contacts as spam, which also appends their IP to the site-wide disallowed_keys option), and perform other state-changing actions via a forged request granted they can trick a site administrator (or any user holding the relevant Groundhogg capability such as delete_contacts/edit_contacts) into performing an action such as clicking on a link.

Severity: N/A

CVSS Score: N/A

Bizum Pay for Android incorporates static values within the APK to authenticate and sign requests to its API, including those for user registration. These values are common across different installations and can be extracted from the APK. An attacker who obtains the application could reuse them to generate requests that the server accepts as authenticated. The potential scope of these requests was limited to querying auxiliary information and certain configuration statuses. Under no circumstances could they generate unauthorised payments via Bizum Pay, nor could they carry out illegitimate activations of the app (which always require access to the customer’s banking channels, thereby protecting them from this type of potential vulnerability). Furthermore, requests are always limited to a set number of attempts and are closely monitored to prevent potential mass queries. The correction implemented uses site-specific material and removes support for the previous format in the backend. Consequently, previous versions are no longer operational for the services affected.

CVE-2026-136638

Published: 2026-11-26 03:17:09 CDT

Severity: MEDIUM

CVSS Score: 5.9

Pydantic AI Harness's PlaywrightBrowser applies an egress policy to the requests a page makes. It treated any URL containing a backslash as having no host, and it allows script and asset requests with no host. A page script could therefore add a backslash to a URL's query to send requests to private addresses, to hosts outside allowed_domains, and to hosts in blocked_domains. This affects applications that use PlaywrightBrowser to open pages or follow instructions an attacker can influence. It applies to fetch, XHR, sendBeacon, WebSocket and passive asset requests. Navigation and frames were not affected. A policy that limits every request kind to an allowlist did not prevent data from being sent to another host. Responses from private services could be read only when the service permits cross-origin reads or accepts the WebSocket connection. Current Chromium versions separately block many requests from public pages to private addresses, but not requests between public hosts, and not when the browser runs behind a forward proxy. The assumed attacker is a third party with no access to the application who controls script on a page the agent opens, or content that steers the agent's browser tools. Upgrade pydantic-ai-harness to 0.74.0 or later. Until then, enforce egress outside the browser with a firewall or a filtering proxy, and do not rely on the browser's domain lists for untrusted pages.
